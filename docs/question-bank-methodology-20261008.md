# 活跃题库出题方法论（题库版本 20261008）

## 1. 目标和边界

本版固定为 30 题：编码 10、工程 10、推理 10。三栏分别计算百分制，不合成跨栏总分；严格通过仍是该题满点。本文和三个分册是设计稿，不替代题库实现、运行器或评分器；题目在完成独立 fixture、参考行为和边界复核后，才能写入活动 manifest。

被测目标是 DeepSeek Flash 单次作答的区分度，而不是通过率本身。30%--40% 是待复测的校准区间，不是设计阶段可以宣称的结果。题目必须先过质量门禁：真实使用者、错误代价、唯一主能力、迁移价值和机械判分五项都要能回答。

## 2. 难度梯度

| 档位 | 编码 | 工程 | 推理 |
|---|---|---|---|
| A | 单一状态机和一个全局约束 | 一个愿望、两个接口、两类状态 | 两段时间线、一个状态转移 |
| B | 两个相互影响的状态视图 | 三个接口、默认值和幂等交错 | 三段时间线、两个资源约束 |
| C | 恢复/重建/回放，跨语言入口一致 | 既有条件叠加但不公布码表 | 多实体交错、反事实或边界时刻 |
| D | 失败保全、版本兼容和全局最优 | 只有少量观测点，正负两本账 | 约束改变最优解，输出仍为小 JSON |

每栏各放 2 道 A、3 道 B、3 道 C、2 道 D。难度来自依赖关系和状态转移，不来自题面长度。删掉任何一个关键条件时，参考答案的至少一个关键字段必须变化；否则该条件只能是背景，不应进入主测。

## 3. 编码难度提升原则

编码题统一采用 Python、Go、TypeScript 三种入口，同一业务契约必须得到同一 JSON 结果。题面明确输入域、输出结构、默认值、排序、时间单位、幂等、错误保全和边界；不使用“每组四分”的合同式题面。

难度可从以下机制组合产生：

1. 需求复杂度和约束交互：局部可行不等于全局可行，多项业务目标需要同时成立。
2. 状态复杂度：双时间/多版本视图、跨实体状态和恢复/重建/回放；失败不会偷偷改变另一份状态。
3. 时序与逻辑复杂度：事件先后、半开窗口、迟到输入、边界时刻或反事实约束会改变状态转移和最优结果。
4. 明示的反常规约束：用于检验指令遵循，例如真实业务迁移期间必须保留的兼容/隔离行为。它必须出现在题面并有业务理由；不以隐藏规则、违背题面常识或猜作者意图制造难度。
5. 可核实的版本兼容行为：包括业务系统版本状态，也包括指定版本的热门/非热门第三方库 API、弃用/移除/新增接口和行为变化。

第三方库题不是禁止项，而是需要单独的题型与执行画像。它测的是“指定版本下能否选对 API 并完成业务行为”，不做脱离任务的 API 冷知识问答。设计时遵守以下约束：

- 只选真实存在、对目标模型不过新的稳定版本；偏门库和热门库都可覆盖。写题前记录目标模型知识时点的证据来源，不能把模型不可能见过的新版本当难度。
- 指定精确包名和版本。版本差异必须有官方文档、发布说明或源码标签作依据，指出新增、移除、签名变化或行为变化；“我记得 API 不同”不算证据。
- 保留真实业务锚点和足够上下文，库 API 是实现路径，不是隐藏答案。不同合法 API 只要在锁定环境下产生相同业务结果就应得分；评分观察外部行为，不检查模型是否写了某个指定符号。
- 若某库行为无法在封闭夹具中稳定复现，或只有提供 API 摘录才能唯一判分，该题标记 `probe`，不进能力主测。不得把文档缺失、网络状态或安装失败算模型错。
- 每个语言入口绑定独立 `runtime_profile`：语言运行时、依赖锁文件/hash、解析来源、编译/执行器版本。Python/Go/TypeScript 的库名可不同，但 fixture、业务契约和判分语义必须一致。
- 评分执行前由独立 resolver 按题目声明的锁文件安装/准备依赖；缓存键由 profile 与 lockfile hash 决定。默认执行不需要容器或新 daemon，安装在临时 HOME 和 profile 缓存中，Python 使用带 hash 的 wheel lock 且只收二进制包，Go 使用 `go.mod`/`go.sum`，TS 使用 `package.json`/npm lockfile。安装只访问配置包源并禁用 lifecycle/build scripts；模型代码实际运行时禁网，不继承包管理器凭据。缺工具链记 `missing`，版本/hash 不符或安装基础设施故障记 `error`，不记模型 fail。
- 不接受模型答案提供的依赖声明或安装命令。当前本机执行后端适配 macOS、Windows、Linux 上已安装的语言工具链；不承诺进程沙箱等价于 OS/VM 强隔离。若题库风险级别要求抵御恶意代码，之后再按平台接入可选强隔离后端，不把 Apple Container 设为跨平台依赖。

20261008 的编码题仍全部使用标准库；`runtime_profile` registry/resolver 已实现，但当前没有 active 题绑定 profile。引入具体三方库题前，仍须完成该库版本证据、逐语言锁文件与行为 fixture/scorer 验证，再纳入 active 分数。

编码题不再以清晰业务清单下的小型全新实现作为主要难度来源。每题应组合至少两种彼此可区分的难度轴（需求/约束、状态、时序/逻辑、指令遵循、指定版本 API/抗幻觉）；打分器仍以多输入、边界、状态交互和失败路径上的细粒度接口行为断言为主，避免只凭单点样例或目标 API 名称判分。

## 4. 工程难度提升原则

工程题继续使用许愿式接口。每题只有一个生产愿望、接口、字段和默认值，以及一句统一 code 规则；题面不写判定结论、码表、公式或“因此不能”。计入 20 条关系的操作必须是题面列出的。夹具里未计入关系的额外操作不参与净分。

评分保持行为观察：20 条关系，每条一分；关系成立记正分，两边都观察到但不一致记负分，缺字段为空缺；净分为正分减负分。参考实现必须 20−0。工程栏报告正分、负分、净分和严格通过，不能借禁项清单继续压分，也不能把低分承诺成目标证据。

## 5. 推理难度提升原则

推理题日志只承载业务事件。每题提供可执行的具体数据、时间线、状态定义、边界归属、输出字段和唯一答案。噪声行、重复编号和 `ignored/dup` 数量不作为主要得分点；最多用于检验事件是否改变状态。

推理题的主能力只选“推理”。指令遵循、幻觉控制和知识广度作为题面约束或排除条件，不另拆成隐藏分。每题 20 分，按字段分组，整组相等才得分；某一组错误不能抹掉其他组已经得到的分。

## 6. 设计审查清单

- 真实流程中的使用者和输入来源是否明确？
- 错误会造成付款、排程、权限、库存、合规或解释哪一种损失？
- 主能力是否只有一项？
- 换业务名词和数据后，核心决策是否仍成立？
- 输出是否能由规则或固定参考行为比较？
- 是否存在第二种合理读法？有则先改题面。
- 关键规则删掉后，参考答案是否变化？不变化则删掉该规则。
- 是否误用了无关日志、题面外操作、隐藏反常规规则或评分器钩子？
- 参考实现是否满点，且正例、边界例、反例均已独立复核？

## 7. 校准和报告

首次落地只记录题面版本、fixture hash、参考实现版本、模型、采样次数、超时和三栏分项结果。编码按语言分别报告可用工具链后的分母；工程同时报告正分、负分、净分和严格通过；推理报告 200 分满分下的百分制和严格通过。任何情况下都不输出三栏合成总分，也不以一次样本把 30%--40% 说成已达成。
