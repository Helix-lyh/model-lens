# 工程能力题库设计（2026-09-26）

本文定义工程栏的设计边界，不是模型能力结论。工程题独立于推理栏、CP 编码栏，
不进入原 24 题的 `pass@k`，也不产生 0-100 总分。

## 先分清题面和评分表

题面只给一个真实业务需求、公开入口、输入输出协议和运行限制。题面不列“请考虑
账号隔离、幂等、审计、锁定”等评分词，否则模型是在按清单填空。

评分表冻结在评测端，按黑盒行为观察。没有观测能力的性质不计分：例如仅凭
`solve(events)` 的返回值，不能证明内部一定用了不可逆哈希、数据库事务或安全随机数。
这类要求要么提供受控依赖和可观察接口，要么降级成“响应不回显秘密”等可证性质。

所有工程题都采用 `solve(events) -> results` 的确定性批处理形式，只让事件中的时间
参与判断。这样既能在无工具模型上复现，也不把网络、数据库和操作系统差异误当成能力。

## E-01 评分账

E-01 当前有 10 个可观察义务：

1. 正确注册和登录能建立可用会话；
2. 未知用户与错误口令的失败结果等价；
3. 响应和可见轨迹不回显提交的口令（不宣称内部哈希）；
4. 连续失败会临时锁定，窗口结束后能恢复；
5. 两次独立成功登录不会复用同一会话标识；
6. 登出前请求成功、登出后同一会话请求失败；
7. 同一 `request_id` 的重试返回同一有效结果；
8. 一个账号被锁定不影响另一个账号登录；
9. 未知事件和伪造会话默认拒绝。
10. 每个输入事件都有一个对应的 JSON 兼容结果，不能靠丢行逃避判定。

每项只有 `covered`、`gap`、`unobserved` 三类结果。正确登录是安全项的功能前置条件，
全拒绝实现不能拿到“秘密未回显”或会话安全分。夹具异常、超时、缺工具链只进入
`unobserved`，不计成风险触发。

风险负债账不与义务账相抵：

| 等级 | 当前可观察风险 | 权重 |
| --- | --- | ---: |
| critical | 伪造会话生效、秘密出现在响应/轨迹、非法输入放行 | 6 |
| high | 登出后仍能访问、锁定永久化且无恢复 | 3 |
| medium | 两类失败对外可区分 | 1 |

同一事实只记一笔风险；无证据不扣分。报告至少包含：

```json
{
  "obligations": {"covered": 9, "total": 9, "gap": 0, "unobserved": 0},
  "risk_debt": {"critical": 0, "high": 0, "medium": 0, "weighted_points": 0}
}
```

严格通过条件是全部可观察义务覆盖且风险账为零。没有 `score10`，不和 CP 的 20 分制
拼接，也不因代码短或多写无害功能加减分。

## 其他场景的评分设计

E-01 到 E-06 每题固定 10 个正向义务点；参考回放必须得到 `positive_points=10`。已证实的
坏行为按风险类别各扣 1 个 `negative_points`，净值为 `net_points=positive_points-negative_points`。
负向扣分不把正向覆盖抹掉，必须同时报告两本账。严格通过条件是正向 10 且负向 0。
实网结果按题目分别报告 `obligations.covered/total`、`positive_points`、`negative_points`、
`net_points`、风险账和严格通过数，不把六题相加成一个工程百分比，也不把工程结果混入
推理/编码栏的 `mean_score10`。

六道工程题全部纳入时，工程栏自身的合成账最高为 60 个正向点：
`max_positive_points=60`、`positive_points`、`negative_points`、`net_points` 和
`strict_passed`。这是工程栏内部的计数账，不是全库总分，也不参与三栏加权。

### E-02 支付回调

题面只说：事件包含商户、订单、金额、状态、签名、版本和 `request_id`；事件可能重复、
乱序、延迟或重放。评分观察：签名失败不改变状态；同一事件重放不重复记账；状态迁移
不倒退；金额和商户不可串线；处理失败可安全重试；已确认订单的旧回调不覆盖新状态。
不能仅凭返回值判定“用了防重放数据库”或“验签算法安全强度”，需提供确定性验签依赖。

### E-03 库存预占

题面只说：库存有预占、确认、释放和超时；请求可重试，取消与确认可能交叉。评分观察：
可售量不为负；同一幂等键不重复扣库存；确认只消耗自己的预占；释放/超时可重放；
过期预占不能再次确认；不同租户和商品不互相污染。并发原子性必须通过交错事件观察，
不把锁的具体实现当得分点。

### E-04 文档抹除与审计留存

题面只说：删除请求会与读取、账务和审计交错；重复请求和跨租户同名 id 存在。评分观察：
删除后普通读取拿不到用户内容；账务金额仍可核对；审计不含可识别正文；重试幂等；
租户 A 的 id 不可访问租户 B 的文档。内部加密、存储介质和保留期限不在黑盒评分范围。

### E-05 异步任务调度

题面只说：任务有租户、优先级、依赖、重试和取消；worker 会重复回报、暂时失联或使用
旧协议。评分观察：依赖未完成不启动；重复回报不重复副作用；重试次数有界；取消后
迟到成功回报不能重新完成任务；租户配额和基本公平性成立；状态可从事件恢复。

### E-06 配置发布与回滚

题面只说：配置有版本、环境、灰度范围、审批、回滚和废弃字段；事件会乱序、重复，
旧客户端仍读取旧字段。评分观察：未审批版本不生效；环境隔离；回滚后旧版本恢复；
灰度范围稳定；重复发布幂等；废弃字段按兼容窗口保留但不参与新决策。

## 接入门槛

每个新场景必须先有：公开协议、参考实现、独立于参考实现的用例预期、10 个正向义务、
至少一个会触发负向扣分的实现、一个“只做正向功能”的反例和一个“全拒绝”的反例。
定向测试全绿后才允许单独实网
校准；工程栏通过率不借用 CP 的 30%–50% 目标，也不并进目录题的 `pass@1`。
