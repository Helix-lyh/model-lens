## 用户锁定的出题合同

工程栏和推理栏、CP 编码栏分开。不进原题库的 `pass@k`，不做 0–100 合成分，不用另一个模型判分。

这是许愿式编程，不是把规则写进题面让模型照着实现，也不是把事件账写进题面让模型复述。

题面只留四样东西：

- 一句生产级别可用的业务愿望。六题开头都是「做一个生产级别可用的……」。E-01 是「做一套生产级别可用的注册和登录」。
- 两到三个接口，以及评分器会传入的字段、允许值和默认值。
- 一句 code 规则：不同的状态、不同的错误使用不同的 `code` 和 `reason`；同一种情况使用相同的 `code`。不附码表。
- 运行限制：实现 `def solve(events)`，按顺序处理，返回等长结果；不得使用网络、文件、工具或子进程。

题面不能写判定句。判定句是「因此不能」「只给」「必须」、公式、锁多少次、哪种状态对应哪个 code。字段名和默认值可以留。例如 `notice_version` 不带视为 2 是接口默认；「旧通知不能入账」是判定句，已经删掉。

每题两到三个业务条件，用这两个到三个接口穿出更多场景。不加数据库、Redis、队列，也不靠把事件排列组合拉长来造难度。不同业务用不同的条件，不要六题套同一套「幂等 + 隔离 + 状态机」。

评分器调用 `solve(events)`。每题 20 条关系，一条一分。关系比较两个观测（或一个观测对一个字面量）是否相同、是否不同，模式是相等或包含。字段限于 `code`、`reason`、`session`、`available`、`amount`、`value`，以及有没有 `amount` / `value`、整段 JSON 文本。

- 关系成立：正分。
- 两边都观测到但关系不成立：负分，记 `deduct_<名字>`。
- 有一边没观测到：空缺，不扣分。空输出是 0 正分 0 负分。
- 净分 = 正分 − 负分。
- 参考实现必须是 20−0。本地门槛是 `tests/test_engineering_login.py`，当前 13 项通过。
- 超时不重试；超时按 0 分计入分母，若响应已有可解析阶段则保留阶段分并强制失败。请求错误和夹具执行失败仍不计能力分。

「任意非成功 code」不算做对了异常。要看该相同的是否相同、该不同的是否不同，以及 `session`、`available`、`amount`、`value` 这些载荷。

## 现行优化策略

先拿上一份答卷在本地重放，看它哪条关系是真做对，哪条是被计分方式放过。不要先改题面。

压得动分的做法：

- 让两三个已经写在接口里的条件叠在同一次调用上。E-02 的例子是：旧通知先于金额被拒绝，所以同一次 `event_id` 之后仍能用新通知入账；附加费订单按应收金额判断，不按订单原额。这些句子不写进题面，只写进隐藏场景和参考实现。
- 关系要打在模型实际判错的那一步。回调 code 和查询 code 分开记。模型把查询收成一个 code 时，「未付的查询 code 等于另一笔未付」会自动满分，哪怕它已经把坏签名入了账。这种关系要改成「这笔查询不能看起来像已付」，或者直接比回调 code。
- 同一条业务只占少数量分。v3.3 草稿里 E-02 曾经因为查询 code 全相同连扣 8 次，净分到了 −12。后来收成 4 条不同的查询状态，其余放在回调上。参考实现仍是 20−0，上一份答卷重放是 8−12=−4；新样本实网是 11−9=2。
- 题面没列出的操作不能出现在隐藏调用里。E-06 删掉 `APPROVE` / `ROLLBACK` 之后，净分从 5 升到 18。参考实现里可以暂时留着死分支，隐藏用例不能再发这些操作。
- 缺字段造成的空缺不要当成扣分。若这个失误应当扣分，就改比双方都一定有的 `code`。E-06 的「拒绝后再批准」原先比值，模型没发布就没有 `value`，变成空缺；改成读结果 code 必须不同于空读，才扣上。

压不动或会抬分的做法：

- 把判定句写回题面。模型会照着做成满分。
- 只加「两种情况 code 必须相同」。一个 code 打天下的程序会把这些分拿满。
- 用题面没写的操作、或者和接口解释相反的隐藏规则造难度。
- 把 `min_client` 这类模型已经做对、参考实现却没做的行为补进评分。那是给当前样本送分。E-06 的 `min_client` 仍是接口字段，v3.3 没有给它计分。
- 用 0/5/10/15/20 的分档代替一条一分。用户要的是得分点、扣分点的个数靠近 10，多了用 15 或 20。现行就是每题 20 条、每条 1 分。

改接口或隐藏场景前先升 `ENGINEERING_VERSION`，并改 `tests/test_engineering_login.py` 里的版本断言。参考实现和模型题面互相独立：参考实现可以编码隐藏行为，题面不能把这些行为说出来。

## v3.3 三题改了什么

E-01。`REQUEST` 可以带 `client`，不带视为不限制。隐藏场景增加了一次老客户端登录后，分别用新客户端和老客户端去请求。锁定期的 code 改为必须不同于窗口结束后的 code；只实现「永远成功」不再能拿回恢复分。场景里的 `LOGOUT` 已删除。参考实现仍保留 `LOGOUT` 分支，但用例不再发送。

`T115945` 扣分：`client_diff`、`client_use`、`gen_codes`、`locked_vs_later`、`locked_vs_ok`、`retry_session`。成功登录的 code 没有按客户端和用户代分开；请求上的 `client` 与登录时不一致仍当成功；锁定没有单独 code；同一次重放没有交回同一个 `session`。

E-02。题面未改。隐藏场景增加了两段交错：版本 1 的通知被拒绝后，同一 `event_id` 的版本 2 仍应入账；附加费订单上的版本 1 通知要先于金额错误被区分开。查询侧只保留四条不同状态：已付对未付、退款对已付、附加费对平费、坏签名对已付。回调侧覆盖签名、旧通知、附加费短款、跨商户相同 `event_id`、旧通知不消耗 `event_id`。

`T115945` 扣分：`badsig_cb`、`badsig_vs_paid`、`legacy_cb_vs_pay`、`legacy_retry`、`legacy_signed_cb`、`replay_cb`、`surcharge_cb`、`surcharge_short_cb`、`ver_before_fee`。查询状态这次分开了。签名、旧通知和附加费金额仍没做对，重复 `event_id` 的回调 code 也没和第一次分开。

E-06。题面未改。隐藏用例不再发送 `APPROVE` / `ROLLBACK`。新场景是：未批准的新版本，换一个 `request_id` 再批准，发布，回滚，再发布，读到的应是新值。另外四条关系改为比较 code：拒绝后再批准的读取不能像空读、另一个环境复用 `request_id` 不能像空读、`approved` 为真和为假的提议 code 必须不同、省略 `approved` 和明确批准的 code 必须不同。

`T115945` 扣分：`approved_vs_flag`、`forward_b`、`hold_ship`、`omitted_vs_yes`、`request_cross`、`string_false`、`unapproved_cb`、`unapproved_read`。批准状态被收成同一个 code；跨环境 `request_id`、回滚后再向前、字符串 `"false"` 都没按参考实现分开。
