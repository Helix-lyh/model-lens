# 20261008 活跃题库设计总稿

## 1. 题量选择

选择 **30 题：编码 10、工程 10、推理 10**。现有三栏已经覆盖账号、支付、库存、配置、交通、门诊、配送、调度等决策；本版用编码的跨语言同契约补足实现迁移，用工程的四个新愿望补足生产接口，用推理的十个跨业务时间线补足状态复杂度，不需要额外 10 题才能覆盖业务决策。

三栏独立报告。编码按可用语言分母计算，工程分别报告正分、负分、净分和严格通过，推理按 200 分满分计算；不输出跨栏总分或简单平均。

## 4. 自检

### 4.1 数量和分数口径

编码 10、工程 10、推理 10，共 30 题；没有跨栏总分。编码每题 20 个观察点并按 Python/Go/TypeScript 可用工具链分别计分；工程每题 20 条关系，正负两本账；推理每题 20 分，栏满分 200。

### 4.2 难度来源审查

没有用无关日志、重复编号、隐藏规则、题面外操作或猜评分器制造难度。20261008 编码题先采用标准库，原因是当时运行器没有按题隔离三方依赖的 runtime profile；这只是当前实现边界，不是难度方法论排除三方库 API 题。后续编码题可以组合业务约束/状态/时序复杂度、明确业务来源的反常规约束和指定版本库 API 熟悉度；版本必须由官方资料证明且不能越过目标模型知识时点，评分继续采用细粒度接口行为测试。工程新题不增加禁项清单；推理日志只保留业务事件。

### 4.3 参考答案审查

编码参考行为使用独立状态表和临时副本，正式落地前要由第二套模拟器核对；工程参考实现必须在本地得到 20−0；推理参考答案已按题面事件逐题手算，但接入评分器前仍须用独立小程序重算并做关键规则删除测试。当前文档不宣称这些测试已经运行。

### 4.4 Flash 仍把规则题做满时的风险

这套设计不会因为“把题面写长”就自动落到 30%--40%。最大风险是编码的 JSON 状态机仍被模型一次性正确实现，尤其 CP-09、CP-13、CP-16；推理中输出字段较少的 NX-11、NX-14 也可能高分。风险控制是：

1. 编码正式 fixture 必须跨语言共享同一组交错案例，并加入恢复/失败保全的反事实对；不能靠继续加条款。
2. 推理先用独立模拟器确认删掉任一关键规则会改变答案，再在 280--600 行的合理范围内调节事件数量；不增加无关行。
3. 工程不以“压到目标”为验收条件，先核对每题 20−0 和已有答卷重放，再单独校准。

若复测仍高于 40%，优先改上述三类高风险题的状态交互，而不是放宽目标、增加题面长度或加禁项。若复测低于 30%，先检查是否存在歧义、工具链缺失或参考答案错误，再讨论难度。
